# 128K build (branch `elite128`)

Rules for `src/elite128/`, `src/viewer128/`, `tools/*128*` and `tools/tests/*128*`; the root `CLAUDE.md` rules still apply (originals in `disks/`, git, docs). Read `README.md` here first; memory map and free bytes: `docs/_memory_map_128k.md`; overview `docs/_128k_version.md`, open work `TODO_128K.md`, diary `CHANGELOG_128K.md`.

- `src/elite128/` is a fork of `src/elite` for a 6128 (filled ships from RAM bank 6, missions and `LARGEAXX` copied from banks 4/5). ONE variant: flags are in `config.inc`, no `-D` flags on the command line except `-DFL_x`/`-DOVL_x` for the mission images. Generated inputs live in `work/elite128/` and are never committed.
- Build: `bash tools/check_src128.sh` (runs `tools/ship128.py`, assembles all, builds `work/elite128/fill.bin` with `-DDB_*` addresses, writes `c128.sym`), then `python3 -I tools/build_dsk128.py` (or `make disk6128`) -> `build/elite128.dsk`, then `cp build/elite128.dsk work/xray/disk/elite128.dsk`. Tests use `DISK128=disk/elite128.dsk` (cpcxray's own `disk/`).
- **Relocation gotchas.** After ANY size change in `commonxx.asm`, cross-file `equ` lines go stale (`common2x.asm` and `largeaxx.asm` call its labels): everything assembles and the game crashes at runtime. `check_src128.sh` now fails on it; fix with `python3 -I tools/gen_equs.py src/elite128 --write` and `python3 -I tools/sync_equs.py src/elite128 --write`. `sync_equs.py --check` exits 1 when stale (that is what `check_src128.sh` runs); without an option it only reports. Then `python3 -I tools/check_moved_labels.py` (raw numbers that still point at a stock address whose label moved; a hit can be a coincidence, e.g. `ld bc,0x1818` ink values).
  `check_moved_labels.py` does not see raw addresses inside `db` blobs: after a size change grep them (`0xC3/0xCD, lo, hi` with a target in `&8060-&9FFF`; most hits are graphics bytes). `dat_8427` (marked Asp's escort) kept a raw `jp &84E0` that was stale from the first spawn change until 2026-11-21; it is a label now.
- `work/elite128/c.sym` belongs to `tools/ship128.py` (the stock build's symbols, regenerated only when older than `src/elite/commonxx.asm`): never write other symbols there. The 128K ones are in `c128.sym`. Symbols for breakpoints must be built with the disk's flags (`sjasmplus --sym=...`, flags from `config.inc`).
- 128K RVM state: `python3 -I tools/rvmstate.py STATE --sna OUT.sna --curcfg` (RAM configuration from `curCfg`, via `c128.sym`). Without `--curcfg` the banks are wrong. RVM writes page 0 last in the file.
- Tests (`tools/tests/test_*128.py`, cpcxray, from `work/xray`; `work/xray` in this worktree is a symlink into the main checkout, so `output/` files land there: pass absolute script paths):
  - `python3 -I tools/tests/run_all.py --emu128` builds the disk, regenerates `output/docked128.sna` and runs the five tests with an `ALL OK` line (packs, sellall, escdigit, filemenu, music). The rest are screenshots, probes or soaks, run by hand.
  - `test_flight128.py 3` makes `output/flight128.sna` (use 3+ steps: 1 is still inside the launch, ships vanish); `snap_docked128.py` regenerates `output/docked128.sna` for `test_launch128.py` (a stale docked snapshot silently runs the OLD code; the same for `output/flight128.sna`: run `test_flight128.py 3` again after every build before a script that loads it); `test_flip128.py` (banks equal after each flip), `test_isrjitter128.py`, `test_hulls128.py` (spawn at most 3-4 types per run, `POS=x,y,z`), `test_order128.py` (`ZS=`), `test_soak128.py N`.
  - To patch or check a bank (bank 7 code, bank 4 copies) never use `memory_write`/`memory_read` at `&C000+`: a run stops at an arbitrary point, often inside a far call (config C6, bank 3 at `&C000`). `sna_save`, edit or read the file at `0x100 + n*0x4000 + offset`, then `disk_insert` and `sna_load` (byte `0x41` of the snapshot is the RAM configuration at save time). A "free memory" claim needs this and a write watch, not only a trap that proves nothing executes there.
  - `sna_save` then read bank n at file offset `0x100 + n*0x4000` (the file is flat, banks 0-7); `memory_read` shows only the CPU's current map (a mapped bank hides what is under it), and `view="ram:N"` returned the same bytes for every N. Disc loads from the emulated drive take several emulated seconds: run 10-15 s before reading results. After boot wait about 4 s before `type_text`, or the first characters are lost.
  - cpcxray scripting for BASIC programs: `type_text` (wait=True) only queues the keys, so always `run` afterwards; poll `screen_text` (JSON, `{"lines": [...]}`) every 0.5 s of emulated time for the expected text instead of fixed delays (a disk read or `SAVE` takes several emulated seconds); to read a file a BASIC program wrote, `disk_save` the in-memory disk to a scratch `.dsk` and read it with `dskx` (the emulator's disk is never written back to the file). Game entry check: `breakpoint_add kind=pc address=0x1C82`, `run`, `sna_save`, read the flat banks (`tools/tests/test_tools128.py`).
- After every change to the 128K build, update `docs/_128k_version.md` and `src/elite128/README.md` in the same step (and the root `README.md` where it describes the 128K version), besides `CHANGELOG_128K.md` and `TODO_128K.md`.
- Interrupt and title pitfalls: the ISR (myVBL) runs on its own stack and keeps the interrupted SP in `stack5` (SP below `&C000` = a far call is active and bank 7 is hidden); the interrupt can only call code in banks 0 and 2 or in bank 7 when it is visible; on the title `&0040-&1A3F` holds the firmware's parked RAM (not `LARGEAXX`), so no disc routine may run before `loadLARGEAXX` has put it back (`loadNotMusique` order); the title music's player (bank 7 slot) must not end its PSG writes in `ei`.
  Refinement: the word at `(stack5)` is the interrupted PC; SP below `&C000` with that PC in `&4000-&7FFF` means the fill module runs in C6, so an interrupt may map C1 (`ld bc,0x7FC1`/`out (c),c`), use bank 7 and map C6 back; any other PC with SP below `&C000` (hull glue, boot) is an unknown configuration: do not remap.
- New resident code: the glue has no free byte before `&9C80` (13 before `&9D9E`). Put it in the overlay on `bankInit` (`lasersights128.asm`, `laserSightsSize` in `commonxx.asm`, copied from the data stage at `STAGE+0x700`, slot of 256 bytes, 231 used by the laser sights, the music hook and the three spawn stubs; the spawn rules are in the bank 6 module `spawnmod.asm`, `&4600`, staged at `STAGE+0x3000`) or in a far-call module.
- `bankInit`'s boot code is part of the glue: every byte added there counts against `&9C80` (the 19 bytes of the spawn module's copy were paid by dropping `ld bc,0x7FC4 / out` and two `ld de` that the previous `ldir` had set already). Blank blocks of the window page for staging (`STAGE+off`, checked 2026-11-21 on the built `COMMONXX.BIN`): `+0x0090-+0x05FF` and `+0x3800-+0x3DFF`; `+0x3000-+0x323F` holds the spawn module, `+0x1C80-+0x1DFF` and `+0x2480-+0x25FF` (0x180 each) are free behind the overlays.
- Several `ldir` blocks in `bankInit` share DE (the next block starts where the last ended): inserting a block in between, or dropping a `ld de`, silently sends data to the wrong bank 6 address (the pack records once landed at `&4840`). `tools/tests/test_spawnvar128.py` compares bank 6 after boot with the build's files: run it after touching `bankInit`.
- The two screen banks must stay equal in the cockpit: the flip syncs by zones (`dbZCompass`, `dbZScanner`, `dbZIndic` in `fill.asm`) plus a full copy when a watched variable changes or every 64th flip. An indicator drawn only on events and not inside a zone that is synced while the scanner is idle will flicker. To desync the banks in a test, edit the snapshot (`sna_save`, patch `0x100 + bank*0x4000`, `sna_load`); a `memory_write` at `&4000` hits the draw bank, which becomes the shown one at the next flip.
- Timing without listening: sample a resident state byte (e.g. `musicState`) every 53 ms of emulated time (not a multiple of 20 ms) for a few hundred samples and compare the histograms before and after a change (the music went from 40% on time to 93% this way).
- The ship-pack hulls (types 20-28) exist only while their flight image is loaded (`mxShipTableImpl` in the default image is just `ld hl,shipGFXdataTable`; a pack swaps types 16/17 and so on by coin flip): never measure them by calling `spawnShip` with type 20+ in the default image, load the pack first. Flag byte `+33` of a slot is blueprint byte `+18` AND `&6F`; bit 2 = hostile (the pack hulls that replace Sidewinder or Krait have it set).
- Trainer and save tools (`src/cheats`, `tools/cheat128.py`, `docs/_cheats.md` "The 128K build"): the 128K disk carries them. After a layout change `check_src128.sh` / `build_dsk128.py` fail with "STALE": run `python3 -I tools/cheat128.py --write` (puts line 830 into `src/cheats/CHEATB.ASC`), then `tools/mk_editsave.py`, `mk_listsave.py`, `mk_convsave.py` (they embed the 128K save key, read from `src/elite128` by `tools/savekeys.py`), then `bash tools/build_cheat.sh`. The save key is the build's own (the 64K rule that the 104 bytes at `EquipShip` stay stock does not apply in this tree); `CONVSAVE` converts between it and the 64K builds. A label used as a number in the disassembly (`ld bc,buf_7406`) breaks when the label moves: such operands must be literals here.
- 128K compile switches: define them in `src/elite128/config.inc` (`IFNDEF X / DEFINE X / ENDIF`; remove the define for the original behaviour). The overlay `lasersights128.asm` includes `config.inc` itself and gets addresses through `-D` from `laser_sights()` in `tools/build_dsk128.py` (add a `-DNAME=...` there for every external); `commonxx.asm` needs the overlay's offsets as `equ` lines (`musicState`, `musicHook`, `spawnVariance` at `bankInit + offset`, with an `ASSERT` in the overlay that the offset is right).
- A user-visible 128K feature or switch also goes into the main `README.md` "Small improvements" with "(128K only)" (stock features get a **128K** note on their bullet).
- Plans live in `~/.claude/plans/delegated-seeking-aho.md` (128K phases, artefacts, languages, particle explosions, BBC ships, hangar); Elite-A analysis in `docs/_elite_a.md`.
- Frame time: `tools/tests/test_frametime.py` (usage in its docstring, method and pitfalls in `docs/_128k_speedup.md`). Compare builds only in the same scene (`--clean`, check a `--shot`), regenerate `output/flight128.sna` after every build, and take symbols from the build's own sym file: fixed addresses went stale once and produced wrong figures.
- The page-flip copy (`dbCopy`) runs with interrupts ON (no `di`/`ei`, two `nop`s keep the addresses): any ISR code (`myVBL`, `IRSound`, `IRKeyboardInput`, `dbIsr`, the music hook) must stay below `&A000` and must not touch `&4000-&7FFF` or `&C000+`, or a flip copy it interrupts breaks. Check any ISR change with `test_isrjitter128.py` (worst entry 5 us) and `test_flip128.py`.
- 128K frame times are whole video frames (the flip waits for a vsync: 240 ms = 12 x 19.97): a saving shows first as a longer wait. Judge a change by the `--phases` times, not the total.
- Second hull set without losing the stock disk: `HULLS=arcelite DSK128=build/elite128_arcelite.dsk make disk6128`, then rebuild the stock one (`make disk6128`) and `cmp` it with the tested disk, because `check_src128.sh` regenerates `work/elite128/` per `HULLS`. Never start a build while `run_all.py --emu128` runs: it rebuilds `build/elite128.dsk` and `work/elite128/` itself.
