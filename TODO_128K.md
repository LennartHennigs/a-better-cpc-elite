## 3. The branch's own open items

- [ ] **Save key:** decide and check. The README and the plan say compatibility is not required; the branch's `CLAUDE.md` still has the 64K rule (104 bytes at `EquipShip` stay stock), and `check_src128.sh` is a smoke test with no byte comparison, so nothing checks the key today.
- [ ] **Save converter for the 128K disk (BASIC):** a small BASIC program on the 128K disk (like `EDITSAVE.BAS`/`LISTSAVE.BAS`, `src/cheats/`, tokenised by `tools/build_cheat.sh`-style scripts) that reads a commander save from a UK, German or French disk, **detects which version wrote it** (each build has its own key: the XOR-scan against the three game files, as `tools/savekeys.py`/`savedec.py` do on the host; fields in `docs/_savegame.md`), decodes it, re-encodes it with the 128K build's key and **recalculates the checksum**, and writes it as a 128K save. Needs first: the save key decision above (the 128K build relocates the 104 key bytes, so old saves do not load), the key bytes of the 128K build, and a host reference to test against (`tools/saveedit.py edit SAVE --key-disk A --to-key-disk B`, already converts DE to UK; extend or reuse it for the 128K disk and compare its output with the BASIC program's on all three languages). Fits in free BASIC memory only if it does not need the game loaded: keep it stand-alone, `RUN"CONV128` from the 128K disk.
- [ ] **Pirates always appear in the top right of the view (seen 2026-11-21):** find out why and randomise it. First decide where the bias comes from: compare with the 64K build (`elite64.dsk`) in the same situation (if stock also does it, it is the original spawn rule: where a hostile gets its start x/y/z, `-DTRAFFIC` spawn constants and `spawnEscortPack` in `commonxx.asm`); if only the 128K build does, suspect the filled-hull path (the fill clamps to the viewport frame, hulls with a vertex behind the viewer are skipped, queue sort) or the page flip, not the spawn. Test: spawn many hostiles at random positions with `test_hulls128.py`-style `POS=x,y,z` and screenshot where they land. Fix: a random sign for x and y at spawn (or fix the clamp), without moving the 104 save-key bytes or adding resident code (about 15 bytes free).
- [ ] **Split `docs/_memory_map.md` into a 64K and a 128K document:** the file mixes the stock 64K map (`&6000-&6FFF` music slot, the parked block, the `COMMONXX` tails, the mission overlays) with the 128K layout (banks 4-7, the `&4000` window, the stage areas), so a reader of one has to skip the other. Make `docs/_memory_map.md` the 64K one and add `docs/_memory_map_128k.md` for the "128K layout" section and the 128K facts in it (free bytes per bank, glue budget); correct the glue budget while at it (the doc says 172 bytes free before the mission table, measured 2026-11-21 it is 22: the glue ends at `&9C6A`); then fix every link: grep `CLAUDE.md`, `src/elite128/CLAUDE.md`, `README.md`, `TODO*.md`, `docs/`, `src/` and `tools/` for `_memory_map` and for the section name "128K layout" (source comments cite doc sections), and check `docs/_128k_version.md` and `src/elite128/README.md`.
- [ ] **Title music (not working; tried 2026-11-21, nothing committed):** the 64K game plays the Blue Danube on the title and docked screens from `MUSIQUEX.BIN` (a tick, `MusicEventroutine`, called from the interrupt while `flagMusicLoaded` is set); the 128K build dropped it. Findings, so the next try does not repeat them:
  - The player is easy to move: its tick uses no firmware (only the start and stop routines called `&BCD7`/`&BCDD`, which can go), PSG writes go through the PPI ports, and two instructions of the tick hide absolute `&61xx` addresses in `db` runs (`ld a,(&6160)`, `ld hl,(&6161)`, `call &6139`: make them mnemonics). Player plus score is 3,611 bytes (`&6000-&6E1A`); the file keeps 4096 bytes (zero tail; the 64K title ship selection that used to live there is resident code now).
  - **There is no home for it.** The interrupt can only call code that is visible in every RAM configuration: bank 0 (`&0000-&3FFF`) and bank 2 (`&8000-&BFFF`). Bank 7 (`&C000`) is hidden while a far call has bank 6 mapped (`hullDraw`/`fillHullEntry`, config C6, bank 3 at `&C000`), which is most of every title frame. `&0040-&1A3F` is NOT `LARGEAXX` on the title: `loadIndicator` (called by `loadMusicnIndicator` at `loc_1CC2`) loads INDICATO to `&0840` and then swaps `&0040-&1A3F` with `&A600-&BFFF`, so the block holds the firmware's parked RAM, which the first docking saves back (`loadLARGEAXX`: `ldir &0040 -> &A600`); a player there would corrupt the firmware RAM (jump block at `&BB00`) the disc routines need. (A test that filled `&0840-&1A3F` with `rst 0` only proved that nothing *executes* there on the title.) `&A000-&BFFF` is the off-screen bitmap, in use on the title; bank 0 core and bank 2 glue are full (about 38 bytes free in total: 22 before `&9C80`, 16 before `&9D9E`).
  - Options: (1) overlay the flight-only 4 KB slice in bank 7 (the old `NOTMUSIC` slice, `loc_604A` is its `+&4A`, about `&DF02-&EF01`) as the 64K game does, restoring it from a generated `NOTMUSIC.BIN` at the title exit, and have the interrupt skip the tick when the stack is not in bank 7 (a far call is active: SP below `&C000`), counting the missed ticks and catching up afterwards: the tune keeps its tempo but gets jitter during every ship fill; costs about 40 resident bytes, which means making the `&9C80` mission table relocatable. (2) A resident player of about 350 bytes with the score in a bank that the interrupt maps in and out (needs a shadow of the RAM configuration written at every `out (c),c` site: risky). (3) Compress the score and decode it in the main loop (large). (4) Music only on screens that make no far call (none today: the title ship is filled).
  - Decide first whether jitter during the ship fill is acceptable; I cannot hear it, so the user has to listen (Virtual Retro).
